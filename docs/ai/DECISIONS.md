## 2026-10-27 — ArgoCD git-ops: single root app-of-apps
**Question:** Three root Applications (`app-of-apps-projects`/`-apps`/`-application-sets` → infra `argocd-system/{projects,apps,application-sets}`, needed because a directory source is non-recursive) or one?
**Decision:** One root `app-of-apps-root` in `hosts-vars-override/<cluster>/argocd.yaml` (`argocd_git_ops_applications`, release `argocd-cfg`) → infra Helm chart `argocd-system/root` whose `values.yaml` holds `appProjects`/`applicationSets`/`applications` arrays (`{name, labels?, annotations?, spec}`); a `guard.yaml` template fails the render when `appProjects`/`applicationSets` is missing/empty or the `applications` key is missing. Root spec: no finalizers *(superseded — the root gets `resources-finalizer.argocd.argoproj.io/background`, rollout pending; see «ArgoCD: full cascade deletion + PVC protection» below)*, SSA+SSD (`ServerSideApply=true` + `compare-options: ServerSideDiff=true`, no `RespectIgnoreDifferences`), automated `prune`/`selfHeal`, `allowEmpty: false`, no sync-waves. AppProject `root` and the `default` lockdown stay in ansible. Steps: 1 — chart added in infra (`6413ec3`); 2 — old roots removed in ansible (`9b6b212`); 3 — override switched to `app-of-apps-root` and applied with `--tags cfg`: all 20 objects (17 AppProject, 3 ApplicationSet) adopted with the same UIDs and no spec change, 34 generated Applications untouched; 4 — old infra directories `argocd-system/{projects,application-sets,apps}` removed with `git rm`, docs updated in both repos.
**Rationale/consequences:** One root, one render, one tracking-id owner. Permanent rules: never delete the root via ArgoCD UI/CLI (API delete is cascade → AppProjects + AppSets, then generated Applications via ownerReferences) — remove/replace only via ansible helm *(rationale superseded 2026-10-27: deletion by any path is now a full cascade by design, see below; the rule itself stays — agents never delete the root, the operator removes/replaces it only via ansible helm `--tags cfg`; a UI/CLI delete wipes everything and the next `--tags cfg` re-creates the root)*; never run a second root over the same objects (tracking-id / selfHeal ping-pong); `allowEmpty: false` is load-bearing; removing/renaming an item in `values.yaml` = prune of that object. `applications: []` stays empty for now (argo-cd #29253). Open: protective annotations (`Prune=false,Delete=false` on AppSets / pol) — operator decision pending, not applied. *(Superseded 2026-10-27: no AppSet/Application-level `Delete=false` — protection moved to the PVC level, see below.)*

## 2026-10-27 — ArgoCD: full cascade deletion + PVC protection
**Question:** Keep the "git-side deletions never destroy cluster data" policy (root without finalizers, protective annotations pending) or make every deletion cascade and protect only the data?
**Decision:** Deletion is **always a full cascade**; **git-ops PVCs are never deleted**. Ansible: in `hosts-vars-override/1520-tech-prod-1/argocd.yaml` (release `argocd-cfg`) `app-of-apps-root` gets `finalizers: [resources-finalizer.argocd.argoproj.io/background]` and AppProject `root` the project finalizer, exactly `resources-finalizer.argocd.argoproj.io`; `charts/argocd/cfg/templates/git-ops-apps.yaml` now renders `finalizers` on AppProjects too. Infra: `argocd-system/root/templates/app-projects.yaml` renders `metadata.finalizers` only when the item passes `finalizers` (parameter, not hard-coded; item model AppProject/Application `{name, labels?, annotations?, finalizers?, spec}`, ApplicationSet `{name, labels?, annotations?, spec}`), and all 17 `appProjects` items in `values.yaml` pass `finalizers: [resources-finalizer.argocd.argoproj.io]`; all 3 ApplicationSets drop `spec.syncPolicy.preserveResourcesOnDeletion` and set `spec.template.metadata.finalizers: [resources-finalizer.argocd.argoproj.io/background]` explicitly (AppSet policy sync patches it onto all 34 generated Applications; the template list is authoritative — manual finalizer edits on generated apps are reverted); `templates/guard.yaml` also fails the render when an `applicationSets` item's `spec.template.metadata.finalizers` holds none of the three finalizers ArgoCD understands — `resources-finalizer.argocd.argoproj.io`, `resources-finalizer.argocd.argoproj.io/background`, `resources-finalizer.argocd.argoproj.io/foreground`, exact match, no prefix matching (a typo such as `/backgroud` would mean no cascade and an Application stuck `Terminating`) — or sets `spec.syncPolicy.preserveResourcesOnDeletion: true`; it does not check project finalizers (optional by operator decision — a project without one makes a root cascade hang for its apps). Applications (root + 3 AppSet templates) use `/background`; projects must use the exact string, never `/background`: ArgoCD v3.5.4 `AppProject.HasFinalizer`/`RemoveFinalizer` (`pkg/apis/application/v1alpha1/app_project_types.go:436-443`) match only it, a suffixed project finalizer is never removed → project stuck `Terminating` forever. Still no sync-waves (finalizers give the ordering; waves would gate the root sync on AppSet Lua health). Data protection: every infra-chart PVC template carries hard-coded `argocd.argoproj.io/sync-options: Delete=false,Prune=false` (`Delete=false` → the cascade skips it, `Prune=false` → removal from git skips it; never put `Delete=false` at Application/AppSet-template level — it would switch off the whole cascade); the `argo-events-cfg` EventBus carries the same (argo-events v1.9.11 `eventbus-controller` finalizer deletes its JetStream PVC together with the EventBus); StatefulSet VCT PVCs survive (retention `Delete` is never set). In ansible, PVCs that are objects (templates) of a helm release — the 8 local-chart `templates/pvc.yaml` (filestash; postgresql in gitlab, outline, seaweedfs, zitadel and mon-system grafana; redis in gitlab, outline) and the portainer/teleport upstream-chart PVCs — are deleted together with the release (`helm uninstall`, template removal) by design, no `helm.sh/resource-policy: keep`; PVCs created by operators or StatefulSet `volumeClaimTemplates` inside ansible-installed components (Prometheus/Alertmanager, Vault, gitaly, seaweedfs, …) are not helm objects and survive `helm uninstall`. All 6 StorageClasses and all PVs are `reclaimPolicy: Retain`, so a deleted PVC's data stays on the released PV. A cluster-wide ValidatingAdmissionPolicy denying PVC DELETE was considered and **deferred** by the operator. Rollout — not done yet, planned order: (1) infra commit: AppProject finalizers (parameter) + EventBus annotation; (2) infra commit: AppSet `/background` finalizers + guard + docs; (3) `argocd-install.yaml --tags cfg`: root (`/background`) + project `root` finalizers. No further step.
**Rationale/consequences:** Project finalizers are load-bearing: the root deletes AppProjects and AppSets in one pass; without them the projects vanish first and every Application fails `finalizeApplicationDeletion` (`getAppProj` NotFound) → `DeletionError` forever, AppSets and root stuck Terminating (verified in ArgoCD v3.5.4 `controller/appcontroller.go`); ArgoCD removes the project finalizer only when no Application references the project, and the root waits while any of its objects still has a `deletionTimestamp`, so the projects go after all their Applications and the root finishes last (this holds with the `/background` Application finalizer). A cascade **deletes** Deployments, Services, ConfigMaps, Ingress/IngressRoutes, ExternalSecrets (target Secrets via GC ownerRef), NetworkPolicies and host Services in foreign namespaces (`traefik-lb`, `haproxy-lb`, `seaweedfs`), Kargo Warehouse/Stage/ProjectConfig (Stage finalizer → Promotions + AnalysisRuns GC-deleted = promotion history lost; Freight has no ownerRef → orphaned, re-associated if a Warehouse with the same name returns, auto-promotion may then re-promote the newest Freight → possible git commit); it **leaves** git-ops PVCs, StatefulSet VCT PVCs (never set `persistentVolumeClaimRetentionPolicy: Delete`), the EventBus (removal is manual), namespaces (ansible-owned), orphaned Freight and cert-manager TLS Secrets without ownerRef. Destructive edits (blast radius): removing/renaming a product/stand directory; renaming `argocd-client/products-with-envs`, `products-no-envs` or `products-kargo/products` (generator returns 0 dirs → every app of that AppSet cascades); editing an AppSet `template.metadata.name` or generator path; renaming/removing an `applicationSets`/`appProjects` item in `argocd-system/root/values.yaml`; deleting `app-of-apps-root` (UI, CLI or removal from the ansible var) = wipe of all product workloads; `guard.yaml` catches only a missing/empty `appProjects`/`applicationSets`, a missing `applications` key, an AppSet template without an exactly matching resources finalizer and `preserveResourcesOnDeletion: true` (not missing project finalizers). The cascade needs live controllers (ESO `externalsecret-cleanup` finalizer on ~40 ExternalSecrets, Kargo `kargo.akuity.io/finalizer` on Stages, argo-events): never uninstall ArgoCD, `argocd-cfg` (it also holds the controller RBAC), ESO, Kargo or argo-events while the root exists — delete the root first and wait until it is gone. Stuck deletion runbook — [`GOTCHAS.md`](GOTCHAS.md). Open (no VAP): manual `kubectl delete pvc` and namespace deletion (incl. removing an entry from `cluster_base_namespaces_list` — the namespace goes with its PVCs, git-ops ones included; the PV stays `Retain`) still delete PVCs. Latent risk: 29 Namespaces carry stale tracking-id annotations (`<ns>:/Namespace:/<ns>`) from before infra `9ae22e8` — harmless while the in-cluster cluster Secret keeps `clusterResources=false`; strip them before ever enabling `clusterResources`, or the cascade would delete those namespaces.

## 2026-10-28 — Argo Workflows: developer launches = argo CLI via local kubeconfig, Strict mandatory
**Question:** How do developers (and Claude Code on laptops) start the predefined WorkflowTemplates — anonymous trigger endpoint (WorkflowEventBinding, second argo-server in `server` mode), argo-server `client` mode with kube-apiserver OIDC, or the CLI's kube mode?
**Decision:** Only **argo CLI v4.1.6 in kube mode** — the same local kubeconfig as `kubectl` (prod-1: Teleport `tsh`; other clusters: their existing OIDC kubeconfig), no `ARGO_SERVER`/`ARGO_TOKEN`; argo-server stays `sso`-only for the UI. Cluster authentication is not touched by this repo for that (kube-apiserver OIDC via `--authentication-config` was rejected). `workflowRestrictions.templateReferencing: Strict` is in `argo_workflows_controller_config_base`, install asserts it is `Strict`/`Secure`. Rejected: WorkflowEventBinding (not needed), second argo-server in `server` mode, copying the SSO token from the UI.
**Rationale/consequences:** Access rights = kube RBAC of the kubeconfig identity in `argo-workflows-cfg` (`create workflows` + `get workflowtemplates` for `--from`); a read-only Teleport role is not enough. Strict checks only `spec`: the `workflows` CRD has no status subresource, so an author-supplied `status.storedWorkflowTemplateSpec` runs instead of the template (verified in v4.1.6 `setStoredWfSpec`) — `create workflows` stays a namespace-admin right until a ValidatingAdmissionPolicy closes it (not done). Under Strict submit always succeeds; a rejected Workflow shows up as `Error`.
