## Operational gotchas

- Prod node SSH is VPN-only (2026-11-11, `cilium_post_ssh_vpn_only_enabled: true`, CCNP `host-firewall-base`): every prod ansible run (playbook-system on nodes, playbook-app via `master_manager_fact`) must come from the VPN. Established non-VPN sessions drop when the policy changes (Cilium checks every packet). Break-glass without VPN: Teleport `tsh ssh` or the OVH console on the manager → `sudo helm --kubeconfig /etc/kubernetes/admin.conf rollback cilium-post <N> -n cilium`, N = a revision whose values have `sshVpnOnlyEnabled: false` ([`COMMANDS.md`](COMMANDS.md)).
- Prod bastion SSH is VPN-only (2026-11-11, `bastion_proxy_haproxy_ssh_vpn_only_enabled: true`, nftables table `inet bastion_ssh`, port 22 only): every `bastion-proxy-install.yaml` run must come from the VPN. There is no Teleport agent on bastion, so without the VPN the only way in is the OVH console: `sudo systemctl stop bastion-ssh-firewall` (`ExecStop` deletes the table; it comes back on reboot or the next node-install run) or `disable --now` to survive a reboot. While an apt repo is unreachable a full node-install fails at the apt task before the firewall tasks — use `--start-at-task "[bastion-proxy-node] Configure fail2ban sshd jail"`. Keep `nftables.service` disabled on bastion — its `flush ruleset` would also wipe the fail2ban table.
- sshd drop-in order (2026-11-11): sshd reads `/etc/ssh/sshd_config.d/*.conf` alphabetically and the **first** value of a parameter wins. On prod (Ubuntu 26.04, OVH) cloud-init writes `50-cloud-init.conf` with `PasswordAuthentication yes` because the provider user-data sets `ssh_pwauth: true` (a `ssh_pwauth: false` file in `/etc/cloud/cloud.cfg.d/` does not override user-data); the image's `60-cloudimg-settings.conf` (`no`) and the old `ansible-hardening.conf` sorted after it, so password login stayed on until DevOps edited `50-cloud-init.conf` by hand on 2026-11-09. Managed sshd drop-ins must sort first: nodes `00-ansible-*` (`prepare-linux-pkgs.yaml`), bastion `10-bastion-proxy-hardening.conf`.
- Config-only `*-install.yaml` runs do not restart workloads: block-scalar configs (`mon_system_loki_config_yaml`, `mon_system_vector_config_yaml`) are mounted from ConfigMaps via `subPath` (`playbook-app/charts/mon-system/loki/templates/loki.yaml:94-97`, `playbook-app/charts/mon-system/vector/templates/vector.yaml:127-131`), and the pod templates carry no config-checksum annotation. subPath mounts never refresh, so after a helm upgrade that changes only the ConfigMap the running process keeps the OLD config until its pod restarts (verified 2026-10-26: Loki retention 744h→600h was in ConfigMap `loki-config-yaml` while the pod kept 744h until `mon-system-restart.yaml --tags loki`). Rule: after `*-install.yaml` with a changed block-scalar config → run `playbook-app/<c>-restart.yaml --tags <sub>`.
- ArgoCD root `app-of-apps-root` (owns the 17 product AppProjects — not `root`/`default`, which stay in ansible (`argocd-cfg` / raw apply) — + 3 ApplicationSets; see [`DECISIONS.md`](DECISIONS.md) 2026-10-27 entries): deletion is **always a full cascade, by design** (code changed, rollout pending). Agents never delete it; the operator removes/replaces it only via `--tags cfg` (helm owns the object: after a UI/CLI delete the next `--tags cfg` re-creates it). The root carries `resources-finalizer.argocd.argoproj.io/background` (cascade with background propagation, like the generated Applications) and AppProject `root` the project finalizer — exactly `resources-finalizer.argocd.argoproj.io`, never with `/background` on an AppProject (ArgoCD v3.6.1 `HasFinalizer`/`RemoveFinalizer`, `pkg/apis/application/v1alpha1/app_project_types.go:436-443`, match only the exact string → a suffixed project hangs `Terminating` forever). The infra `guard.yaml` requires each AppSet template to carry one of `resources-finalizer.argocd.argoproj.io`, `…/background`, `…/foreground` by exact match, no prefix matching (a typo such as `/backgroud` fails the render; ArgoCD would not recognise it → no cascade, Application stuck `Terminating`) and rejects `preserveResourcesOnDeletion: true`; project finalizers are not checked. Ordering comes from the project finalizers: a project is released only when no Application references it, and the root waits while any of its objects still has a `deletionTimestamp`, so the root goes last. Deleting the root — dropping it from `argocd_git_ops_applications` + `--tags cfg`, or from the ArgoCD UI/CLI — deletes all AppProjects + AppSets, the generated Applications (ownerReferences) and, through their finalizers, **every product workload**; git-ops PVCs (`Delete=false,Prune=false` in the infra charts), StatefulSet VCT PVCs, the EventBus and namespaces (ansible-owned) stay. The cascade needs live controllers: never `helm uninstall` `argocd-cfg` (it also holds the controller RBAC → cascade stalls on 403), ESO, Kargo or argo-events while the root exists — delete the root first and wait until it is gone. Never add a second root over the same objects (auto-sync tracking-id ping-pong). `--tags cfg` renders whatever `argocd_git_ops_applications` holds in the checkout it runs from — a stale checkout without `app-of-apps-root` deletes it (= full wipe) or recreates old roots — so keep the override committed and pulled before running. In the override never drop the root's or project `root`'s `resources-finalizer` (nor add `/background` to the project's), never set `allowEmpty: true` or `RespectIgnoreDifferences=true` on the root; keep `ServerSideApply=true` and `ServerSideDiff=true` together. Stuck deletion (Application condition `DeletionError`, Warning event `Unable to delete application resources`): missing project → recreate the project (do not strip finalizers); a resource that cannot be deleted → annotate it live `argocd.argoproj.io/sync-options: Delete=false` (read from the live object), the next pass skips it; stripping Application finalizers is the last resort (orphans the rest).
- PVC deletion model (operator, 2026-10-28): only **git-ops** PVCs are never deleted — the infra-chart PVC templates carry hard-coded `argocd.argoproj.io/sync-options: Delete=false,Prune=false` (the cascade and prune skip them), the argo-events EventBus carries the same, and StatefulSet VCT PVCs are never given `persistentVolumeClaimRetentionPolicy: Delete`. In ansible, PVCs that are **objects (templates) of a helm release** — the 8 local-chart `templates/pvc.yaml` (filestash; postgresql in gitlab, outline, seaweedfs, zitadel and mon-system grafana; redis in gitlab, outline) and the portainer/teleport upstream-chart PVCs — are deleted together with their release (`helm uninstall`, template removal) — intended behaviour; do not add `helm.sh/resource-policy: keep`. PVCs created by operators or StatefulSet `volumeClaimTemplates` inside ansible-installed components (Prometheus/Alertmanager, Vault, gitaly, seaweedfs, …) are not helm objects and survive `helm uninstall`. All StorageClasses/PVs are `reclaimPolicy: Retain`, so the data of any deleted PVC survives on the released PV. A cluster-wide ValidatingAdmissionPolicy denying PVC DELETE is deferred by the operator, so nothing stops a manual `kubectl delete pvc` or a namespace deletion: removing an entry from `cluster_base_namespaces_list` + `--tags namespaces` deletes the namespace **with its PVCs**, git-ops ones included (`Delete=false` does not cover namespace deletion).
