# Cold-start для подготовки обновления компонента (Opus)

Этот файл — промпт, который user копирует в новое Opus chat-окно, когда вышла новая версия **любого** компонента и надо подготовиться к обновлению.

Агент сам достаёт текущую версию из inventory, сам находит исходники и конфигурацию, сам делает разбор диффа и выдаёт go/no-go. От user'а нужны только **имя компонента и целевая версия**.

Привет. Ты готовишь **обновление версии компонента** в проекте k8s-ansible.

Твоя задача — **не обновлять**, а подготовить обновление: разобрать дифф между текущей и целевой версией, найти всё, что ломается или меняет поведение именно в моей конфигурации, и выдать вердикт go/no-go с точными правками инвентаря. Обновление я запускаю сам, по твоему плану.

## Шаг 1. Спроси меня

Спроси одним вопросом: **какой компонент обновляем и до какой версии**. Больше ничего не спрашивай — всё остальное ты обязан выяснить сам. После моего ответа переходи к шагу 2 и дальше работай сам, пока не упрёшься в необходимость выполнить команду на кластере.

## Шаг 2. Установить фактическое состояние (ничего не предполагать)

Всё ниже — **проверить**, а не додумать:

- **Текущая версия из inventory.** Три схемы пина, определи, какая у компонента:
  - helm-чарт: `<c>_helm_chart_version: "X.Y.Z"` в `hosts-vars/<c>.yaml`;
  - вендоренный манифест с явной переменной: `<c>_version: "vX.Y.Z"` (+ образ через неё);
  - вендоренный манифест без переменной — версия внутри самого файла в `playbook-app/charts/<c>/`.
- **Не перекрыт ли пин в override.** Кластеры лежат в `hosts-vars-override/<cluster>/` (сейчас: `test-1`, `1520-tech-prod-1`). Значение в override **побеждает** базовое. Проверь оба кластера — версии и топология у них разные.
- **Исходники.** `sources/<c>/` — обычно git-репозиторий апстрима. Осторожно:
  - тег целевой версии может быть **не подтянут** (`git tag --list`), хотя сам релизный коммит уже в HEAD — сверь `git log -1 --format='%s'` и файл версии/чарта в HEAD, прежде чем говорить «версии нет»;
  - HEAD может быть **дальше** релизного тега (N коммитов после) — тогда локальный код ≠ то, что уедет в образ.
  Диффай **тег к тегу**, а не к HEAD, если тег есть.
- **Доступность апстрима.** Для helm-компонентов проверь, что целевая версия **опубликована** в репозитории чартов (`curl -s <repo>/index.yaml | grep 'version: X.Y.Z'`). Бывало, что релиз и образ есть, а чарт ещё не выложен — установка падает на `no chart version found`.
- **Что реально задеплоено.** Попроси у меня вывод: `helm list -n <ns>` и образы подов. Inventory может расходиться с кластером.

Итог шага — короткая таблица: где какая версия, какие кластеры затронуты, есть ли исходники и опубликован ли чарт.

## Шаг 3. Дифф чарта/манифеста — ПЕРВЫМ ДЕЛОМ

Это класс, который ломал прод дважды (иммутабельные поля StatefulSet; переименование ключа в values). Разбирай раньше бинарного диффа.

- `values.yaml`: **переименован / удалён / сменил тип** ли хоть один ключ, который я реально задаю? Ключ, который я не задаю, — не проблема; ключ, который задаю, — блокер.
- Новые шаблоны: под каким гейтом, включены ли по умолчанию, не появится ли новый объект в namespace.
- **Иммутабельные поля**: `spec.selector`, `serviceName`, `volumeClaimTemplates`, `clusterIP`, тип Service. Их изменение = `helm upgrade` падает с `field is immutable`, а `--atomic` может оставить релиз битым.
- **Hooks** (`helm.sh/hook: pre-install/pre-upgrade`): что делают, под каким условием срабатывают, какие права у их Job'ов. Helm **не откатывает** side-effects хуков, и `--atomic` их не отменяет. Отдельно проверь хуки, которые умеют удалять/пересоздавать ресурсы.
- **Проверяй рендером, а не чтением.** Достань обе версии чарта, резолвни мои реальные values и сравни структурно:
  ```bash
  ansible-playbook -i hosts-vars/ -i hosts-vars-override/<cluster>/ <дамп-плейбук> # получить resolved values
  helm template <rel> <chart-old> -f values.yaml > old.yaml
  helm template <rel> <chart-new> -f values.yaml > new.yaml
  diff old.yaml new.yaml     # ожидание: только версия/тег образа
  ```
  Учитывай: `helm template` **не может доказать отсутствие hook-Job'а**, если его гейт построен на `lookup` — под `helm template` он всегда пустой. Такие гейты разбирай по коду шаблона.

## Шаг 4. Дифф бинаря / манифеста апстрима

- Полный `git log --oneline <old>..<new>` — не доверяй темам коммитов, открывай diff там, где это важно.
- Классифицируй каждое изменение: **доходит ли оно до моей сборки и моих путей**. Отделяй другой язык/подсистему (например Rust-крейт рядом с Go-бинарём), тесты, CI, и подсистемы, которых у меня нет.
- Ищи специально:
  - **перевёрнутые дефолты** (флаг был `false`, стал `true` — например телеметрия/phone-home);
  - **переход «хардкод → конфигурируемо»**: значение было зашито, стало читаться из настройки с **другим** дефолтом — тихо меняет поведение;
  - удалённые/переименованные CLI-флаги и изменённые дефолты;
  - изменения формата вывода команд, которые парсит моя автоматизация;
  - переименованные/удалённые метрики (у меня ServiceMonitor'ы скрейпят всё без keep-фильтра);
  - изменения схемы БД/стораджа, требующие миграции.

## Шаг 5. Совместимость при rolling-restart

Во время раската **старые и новые поды сосуществуют** и общаются между собой. Проверь, что изменения протокола/API **строго аддитивны**: новые поля/методы — да; удаление, перенумерация, смена типа поля, изменение сигнатуры метода — нет. Если я пропустил промежуточную версию, проверять надо пару «моя текущая ↔ целевая», а не «предыдущая ↔ целевая».

## Шаг 6. Моя автоматизация не должна сломаться

Проверь всё, что зависит от внешнего поведения компонента:
- ansible-таски и `filter_plugins/*.py`, которые **парсят вывод** команд компонента;
- флаги/подкоманды, которые вызывает мой sync;
- формат конфигов, которые я генерирую.
Лучшее доказательство — прогнать мой реальный парсер на выводе новой версии, а не рассуждать о нём.

## Шаг 7. Проверь себя состязательно

Прежде чем писать вердикт, попробуй **опровергнуть** собственные ключевые выводы: перечитай код по спорным пунктам и явно скажи, что подтвердилось, что понижено в серьёзности, а что оказалось неверным. Если что-то проверить не удалось — так и напиши, не выдавай предположение за факт.

## Известные грабли (проверено на практике)

- Чарт целевой версии может быть **не опубликован**, хотя тег и образ есть.
- Тег может быть **не подтянут** локально, при этом HEAD — уже релизный коммит.
- `kubectl -l <селектор>` может **не выбрать ни одного пода** (метки компонента отличаются от ожидаемых) — тогда `| grep -c` вернёт уверенный `0`, который ничего не значит. Сначала убедись, что селектор кого-то выбирает; при сомнении итерируйся по подам по имени.
- Значение, которое раньше было **зашито в код**, может стать читаемым из настройки с другим дефолтом — поведение меняется молча.
- Hook, включённый по умолчанию, может выполнить деструктивную операцию как побочный эффект рутинного прогона.
- **Не смешивай** правки инвентаря и bump версии в одном прогоне: сначала раскатай защитные настройки на текущей версии, потом меняй версию — иначе не разделишь причины, если что-то пойдёт не так.
- `make test | tail` **маскирует** код возврата make — читай строку `make test → exit 0 (all N stages passed)` или `> log; echo $?`.

## Дисциплина проверки

- Любой скрипт/харнесс проверки **сначала запусти**, потом ссылайся на его результат. Не выводи числа из номеров строк.
- Структурные проверки рендера — через `python3` + `yaml.safe_load`, а не `grep` (grep врёт на folded-скалярах и подстроках).
- Поведение-сохраняющие правки инвентаря доказывай **render-diff'ом** (байт-в-байт, кроме намеренного).
- Правки инвентаря — по конвенциям репозитория: полная структура переменной в `hosts-vars/` (база), per-cluster значения в override, объявление переменной **выше** её потребителя.
- После правок — `make test`, и прочитай настоящий exit-код.
