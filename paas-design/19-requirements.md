# 19. Требования

> Формальный список требований к платформе. Каждое требование — с ID, приоритетом и этапом. Приоритет: **M** — must (без него не запускаемся), **S** — should, **C** — could. Этап: **MVP** или **Ф2** (фаза 2, см. [17-roadmap.md](17-roadmap.md)).
> Как каждое требование реализуется — в профильных документах (ссылка в колонке «Где»).

## 1. Акторы

| Актор | Кто это | Как взаимодействует |
|---|---|---|
| Посетитель | не зарегистрирован | лендинг, регистрация |
| Владелец организации | платит, управляет участниками | консоль |
| Участник организации | admin / developer / viewer / billing | консоль |
| CI пользователя | скрипт, пайплайн | API-токен, Harbor robot-токен |
| Клиент приложения тенанта | конечный пользователь сервиса тенанта | HTTP(S)/TCP к доменам и портам тенанта |
| Оператор платформы | владелец (соло) | админка (VPN-only), Ansible, Teleport |
| Платёжный провайдер | ЮKassa / CloudPayments / T-Bank | webhooks |
| Госорганы | РКН, правоохранительные органы | запросы, СОРМ |
| Абьюз-репортер | третье лицо | abuse@, форма |

## 2. Ограничения (заданы владельцем)

| ID | Ограничение |
|---|---|

| CON-02 | Backend — только Go |

## 4. Нефункциональные требования

### 4.1. Безопасность

| ID | Требование | Пр. |
|---|---|---|
| NFR-SEC-01 | У пользователя нет доступа к kube-apiserver, kubeconfig, ServiceAccount-токенам | M |
| NFR-SEC-02 | Пользователь не присылает YAML/Helm; вход — только типизированная allow-list модель | M |
| NFR-SEC-03 | Все инварианты безопасности пода проверяются на admission (VAP + PSA restricted) **независимо** от backend | M |
| NFR-SEC-04 | Код тенантов исполняется только на выделенном пуле нод; системные компоненты там не исполняются | M |
| NFR-SEC-05 | Под тенанта не может установить соединение с: kube-apiserver, kubelet, IP нод, link-local/metadata, RFC1918, pod/service CIDR других namespace, системными сервисами | M |
| NFR-SEC-06 | Исходящий SMTP (25) закрыт; исходящий трафик тенантов уходит через выделенные egress-IP, не через IP нод | M |
| NFR-SEC-07 | Секреты никогда не попадают в git, логи, ответы API после создания (кроме явного раскрытия с аудитом) | M |
| NFR-SEC-08 | Компрометация интернет-facing процесса (`paas-api`) не даёт права записи в Kubernetes | M |
| NFR-SEC-09 | Каждое изменяющее действие — в append-only аудит-логе (кто, что, когда, откуда) | M |
| NFR-SEC-10 | Сессии — httpOnly `__Host-` cookie; токены не попадают в JS; жёсткий CSP с Trusted Types | M |
| NFR-SEC-11 | Все образы — через Harbor; сканирование Trivy | M |
| NFR-SEC-12 | Консоль и приложения тенантов — на разных регистрируемых доменах | M |
| NFR-SEC-13 | Админка оператора — отдельный домен, отдельный OIDC-клиент (staff), только через VPN | M |
| NFR-SEC-14 | Шифрование в пути (TLS) на всех внешних интерфейсах; etcd encryption at rest (есть) | M |
